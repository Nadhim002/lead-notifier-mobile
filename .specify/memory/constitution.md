# Lead Notifier Constitution

## Core Principles

### I. Single Source of Truth for Session & Device State
There is exactly one `onAuthStateChanged` subscription for the whole app, owned by
`hooks/AuthProvider.tsx` and read everywhere via `useAuth()`. There is exactly one owner of this
phone's stable device id and its Firebase ref: `deviceIdentity.ts`. New code MUST read auth and
device identity through these owners; it MUST NOT open a second auth listener or derive a
competing device id.
**Rationale**: this app's core failure mode is a missed or duplicate lead alert. A second auth or
device-identity source of truth is exactly the kind of divergence that causes a device to silently
stop receiving pushes or register itself twice.

### II. Cross-Repo Wire Contract Discipline
Three formats are shared by convention (not by shared code) with the sibling
`indiamart-extension` repo: notification channel IDs (`channels.ts`), the Firebase project config
(`firebase.ts`), and the Expo push payload shape (consumed in `notifications.ts` /
`useLeadListener.ts`). Any change to one of these three MUST be paired with the matching change in
the extension repo before it ships.
**Rationale**: per `docs/ARCHITECTURE.md`, a channel-ID mismatch makes Android silently drop the
notification — there is no error, just a lead the user never sees. The two repos have no compiler
or type system to catch this for them.

### III. Structured, Tagged Logging Only
Feature code MUST log through the tagged loggers in `logger.ts` (`AppLog`, `AuthLog`, `NotifLog`,
`LeadsLog`, `DeviceLog`, …), not bare `console.log`. Add a new tagged logger for a new domain area
rather than reusing an unrelated tag or dropping to `console.log`.
**Rationale**: notification and lead-delivery bugs are diagnosed from device logs after the fact
(the failure is often "the alert never appeared"); untagged logs make that triage effectively
impossible.

### IV. Native Behavior Lives in Config Plugins, Not Hand-Edited Native Code
Android native behavior required for this app (currently the full-screen-intent incoming-lead
takeover) MUST be generated by an Expo config plugin (`plugins/withFullScreenIntent.ts`) at
prebuild, not hand-edited directly in `android/`. Hand edits to generated native files are
overwritten on the next prebuild and MUST NOT be relied upon.
**Rationale**: this keeps the native project reproducible from source and buildable by EAS/CI
without out-of-band manual native patches.

### V. Custom Dev Client Only, Versioned Docs Only
Expo Go MUST NOT be used or assumed to work for this app — it cannot receive Firebase/FCM
notifications, which is the app's core function. All Expo API usage MUST be checked against the
versioned docs at `https://docs.expo.dev/versions/v56.0.0/` (per `AGENTS.md`), not general/current
Expo documentation, because this project intentionally runs ahead on Expo SDK 56 / React Native
0.85 / React 19.
**Rationale**: assuming current-stable Expo API shapes on this unusually high version set has
already been called out in `AGENTS.md` as a source of incorrect code.

## Security & Secrets Handling

- Android signing keystores (`*.jks`) MUST NEVER be committed. They are `.gitignore`d; any new
  keystore file MUST be verified against `.gitignore` before it is added to the working tree, and
  any keystore found already tracked in git history MUST be treated as compromised and rotated.
- `google-services.json` is tracked in this repo and treated as project configuration, not a
  public secret — it MUST stay out of any public fork, but it is not treated as sensitive as a
  private key.
- Firebase Realtime Database access is governed by security rules that live outside this repo;
  this repo's client config (`firebase.ts`) does not enforce access control and MUST NOT be
  treated as if it did.

## Development Workflow

- There is no separate typecheck script; `npx tsc --noEmit` is the convention for type-checking
  before committing.
- `npm run android` / `npm run ios` (via `expo run:*`) build and install a native dev client;
  `npm run web` is best-effort only — auth and notifications are not fully supported there.
- Dev/QA tooling (`scripts/seed-review-leads.mjs`, `scripts/send-test-push.mjs`) is for local
  verification only and MUST NOT be treated as part of the shipped app surface.
